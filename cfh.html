How the Cloudflare ecosystem works

Concept by concept, like a short story. For anyone curious how apps run on the internet.

Card 1 of 0
1 — The big picture

Where do websites and apps actually run?

When you open a website or use an app, your phone or computer talks to another computer somewhere in the world. That “other computer” is a server. Servers used to be big machines in a room that companies had to buy and maintain.

Today we often use the cloud: someone else runs those computers in data centers around the world, and we just write code and put it there. Cloudflare is one of those “someones”—and they run a huge network very close to where people actually are.

2 — The edge

What is Cloudflare’s “edge”?

Edge means “as close as possible to the user.” Cloudflare has data centers in hundreds of cities. So instead of your code running in one faraway server, it can run in a machine near the person who’s using your app.

That means faster responses and less delay. Think of it like having a copy of your app in many cities instead of in just one.

3 — Code without a server

What is a Worker?

A Cloudflare Worker is a small piece of your code that runs on Cloudflare’s edge. You don’t rent a whole server or install an operating system. You just write a script (in JavaScript, TypeScript, Rust, etc.) that handles requests—like “when someone visits this URL, do this.”

So: Worker = your logic running at the edge. It can talk to APIs, save data, and return responses. You deploy it with a tool called wrangler and get a URL. That’s your “backend” if you want.

4 — Why “state” matters

What happens when you need to remember something?

By default, when a Worker runs, it does its job and then it’s done. It doesn’t “remember” anything for the next request. If you want to remember data—like “this user visited Paris” or “this is the last score”—you need state: somewhere to store and read it.

That “somewhere” is usually a database or a key–value store. Cloudflare gives you both: KV (simple key–value) and D1 (a SQL database).

5 — Key and value

What is a key–value store?

Imagine a wall of lockers. Each locker has a number (the key) and inside is your stuff (the value). You don’t search “all lockers with red backpacks”—you say “open locker 42” and you get whatever is in there.

A key–value store is like that: you put(key, value) and later get(key). For example: key = "France", value = "Paris". No tables, no SQL—just keys and values. Very fast for “give me the value for this key.”

6 — Workers KV

Cloudflare’s key–value store

Workers KV is Cloudflare’s key–value store. You create a “namespace” (like one wall of lockers), connect it to your Worker in wrangler.toml, and in code you do get(key) and put(key, value).

It’s great for caching (e.g. “save this API result under this key so next time we don’t call the API again”) and for simple data like “country → city.” It’s not SQL—no queries, no relations. Keys and values are usually strings (or JSON as a string).

Real example: an app that tracks “cities I visited per country” can store France → Paris in KV. POST /France with { "city": "Paris" } saves it; GET /France returns Paris.
7 — When key–value isn’t enough

When do you need a real database?

KV is perfect when you only need “look up by one key.” But sometimes you need tables, relationships, and queries like “all movies with rating > 8” or “users who signed up this month.” For that you use a SQL database: tables, columns, rows, and a language (SQL) to query them.

Cloudflare’s SQL database is called D1. It’s serverless (you don’t manage the server) and works with Workers. You write SQL (create table, select, update) and run it from your Worker.

8 — D1: SQL at the edge

What is D1?

D1 is Cloudflare’s SQL database (built on SQLite). You define tables (e.g. movies: id, title, release_date, rating) using migrations—files that describe changes to the database. You run migrations locally and then with --remote for production.

In your Worker you do things like: db.prepare("SELECT * FROM movies").all() or prepare("UPDATE movies SET rating = ? WHERE id = ?").bind(10, 1).run(). So your code runs at the edge and the data lives in D1—all on Cloudflare.

9 — Bindings: connecting the dots

How does a Worker talk to KV or D1?

You don’t hardcode passwords or database addresses in your code. In wrangler.toml you declare bindings: “my Worker has a KV namespace called CACHE” or “a D1 database called DB.” Cloudflare injects those into your Worker at runtime.

So in code you write c.env.CACHE or c.env.DB and you get the KV or D1 interface. That keeps secrets and config out of your code and lets you switch between local and production by config.

10 — Front end vs back end

Where does the “website” part live?

The back end is the Worker: it handles API requests, reads/writes KV or D1, and returns JSON or other data. The front end is the thing users see—HTML, CSS, JavaScript in the browser. You can build a “headless” app that’s only an API (no UI); then any client (browser, app) can call it.

If you want a real website (pages, buttons, forms), you can host that on Cloudflare Pages: push your front-end code to Git, connect the repo to Pages, and Cloudflare builds and serves it. So: Pages = front end, Workers + KV/D1 = back end. They can work together.

11 — Where everything actually lives

The full picture

  • Your code lives in a repo (e.g. GitHub) and on your laptop. You edit it there.
  • Runtime: when you deploy, that code runs on Cloudflare Workers (the edge).
  • Data: stored in KV (key–value) or D1 (SQL), both on Cloudflare.
  • Front end (optional): static site on Cloudflare Pages, or any app that calls your Worker URL.

So you don’t “do everything inside Cloudflare”—you keep code in Git and run it on Cloudflare. Wrangler is the tool that deploys your Worker and connects it to KV/D1.

12 — Free tier and cost

Does it cost money?

Cloudflare has a free tier (no credit card for Workers/KV). For example: 100,000 Worker requests per day, KV with 100,000 reads/day and 1,000 writes/day and 1 GB storage. Many small projects and learning experiments stay at $0/month.

When you grow, you pay for what you use (e.g. more requests, more storage). So you can learn and build real apps without paying until you need more.

13 — One sentence per piece

Quick recap

  • Edge = run code and data close to users, worldwide.
  • Worker = your back-end code running at the edge, no server to manage.
  • KV = key–value store; great for cache and simple lookups (get/put).
  • D1 = SQL database; tables, queries, migrations.
  • Pages = host your front-end (static site) on Cloudflare.
  • Wrangler = CLI to develop and deploy Workers and wire up KV/D1.

You write code → Wrangler deploys it to Workers → your app runs at the edge and uses KV or D1 for state. That’s the Cloudflare ecosystem in a nutshell.
