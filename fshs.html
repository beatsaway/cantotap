Full-stack tutorial: Worker + Supabase + Pages

Step-by-step how-to for high schoolers. One repo, auth, API, and front end.

Card 1 of 0
Step 1 — The big picture

What we're building

A full-stack app with:

  • Front end – the page users see (HTML, forms, buttons). Hosted on Cloudflare Pages.
  • Back end (API) – code that saves and loads data. Runs on a Cloudflare Worker.
  • Database – where data is stored. We use Cloudflare D1 (SQL) and connect it to the Worker.
  • Login – so each user only sees their own data. We use Supabase for sign-in and get a token; the Worker checks that token.

Everything lives in one GitHub repo. The Worker uses the repo to deploy the API; Pages uses the same repo and only publishes the public folder as the website.

Step 2 — Create a Cloudflare Worker

Set up the back end (API)

In Cloudflare Dashboard → Workers & Pages → Create application → create a Worker (e.g. “Connect to GitHub” or use a template).

When it asks for a repo, connect your GitHub and pick (or create) a repository. Cloudflare will use this repo to build and deploy your Worker. You get a URL like your-project.workers.dev – that’s your API.

In the Worker’s Settings you can add Variables and Secrets (e.g. Supabase URL and anon key) and Bindings (e.g. a D1 database). The Worker code runs at the edge and can read/write D1 and call Supabase to check login tokens.

Step 3 — GitHub for the Worker

One repo for the whole app

Your GitHub repo (e.g. yourname/chordslash) contains:

  • Worker code – e.g. src/index.ts, wrangler.json. When you push to main, Cloudflare builds and deploys the Worker automatically.
  • Front end files – inside a folder called public (HTML, CSS, JS). We’ll tell Cloudflare Pages to use only this folder later.

So: one repo, two “deployments” – the Worker uses the whole repo to run the API; Pages will use only the public folder for the site. No need for a second repo.

Step 4 — Supabase auth setup

Let users log in

Go to supabase.com → create a new project (name it, set a database password, pick a region). Enable Email signup in Authentication settings.

In Project Settings → API copy your Project URL and the anon (publishable) key. You’ll use these in:

  • Your front end – to sign users in and get a session token.
  • Your Worker – so it can check that token (e.g. add SUPABASE_URL and SUPABASE_ANON_KEY in the Worker’s Variables or in wrangler.json).

Create a test user (e.g. in Supabase → Authentication → Users) so you can try logging in from your app.

Step 5 — Worker: API + auth + database

What the Worker does

Your Worker code should:

  • Handle routes like GET /progressions and POST /progressions.
  • Read the Authorization: Bearer <token> header and call Supabase to verify the token and get the user id.
  • Use that user id to read/write only that user’s rows in D1 (e.g. a chord_progressions table).
  • Send CORS headers (e.g. Access-Control-Allow-Origin: *) so the browser can call the API from your front-end URL.

Create the D1 table (e.g. in Cloudflare Dashboard → D1 → your database → Console) and add the D1 binding to the Worker. Deploy by pushing to GitHub or running npm run deploy from the repo.

Step 6 — Front end in the same repo

Add a public folder

Inside your repo, create a folder named public. Put your HTML file(s) there (e.g. public/test-progressions.html or public/index.html).

In the HTML you:

  • Load Supabase JS and let users log in (email/password). Supabase keeps the session in the browser (e.g. localStorage).
  • When calling your API, send the token: Authorization: Bearer <session.access_token>.
  • Point the fetch URL to your Worker: https://your-project.workers.dev/progressions.

Commit and push the public folder to the same repo. Next we’ll tell Cloudflare Pages to serve it.

Step 7 — Cloudflare Pages from the same repo

Deploy the front end

In Cloudflare Dashboard → Workers & Pages → Create application. At the bottom click “Looking to deploy Pages? Get started”.

Choose Import an existing Git repository and select the same repo you use for the Worker (e.g. yourname/chordslash).

In Set up builds and deployments:

  • Project name: e.g. chordslash (your site will be at chordslash.pages.dev).
  • Production branch: main.
  • Framework preset: None.
  • Build command: leave empty.
  • Build output directory: type public (so Pages serves only the public folder, not the whole repo).

Click Save and Deploy. When it’s done, your front end is live at https://your-project.pages.dev (and e.g. /test-progressions.html).

Step 8 — Adding Stripe payments (optional)

How you might do payments

If you want to charge users (e.g. a “Pro” plan), you can use Stripe. Important: your Stripe secret key must never be in the front end or in GitHub. It stays only in the Worker as a Secret.

  • Worker – Add a route like POST /create-checkout or POST /billing-portal. The Worker verifies the user (Supabase token), then calls Stripe’s API with the secret key to create a Checkout Session or a link to the Customer Portal. Return the URL to the front end.
  • Front end – A “Upgrade” or “Manage billing” button calls your Worker (with the auth token). The Worker returns a Stripe URL; the front end redirects the user there to pay or manage their subscription.
  • D1 (optional) – Store the Stripe customer id or subscription status per user (keyed by Supabase user id) so your Worker knows who is paid and who isn’t.

So: Stripe runs inside the Worker (secret key in Variables/Secrets). The browser only ever gets a one-time URL to Stripe’s hosted page. No payment details touch your front end.

Step 9 — You’re done

What you have now

  • Front end → Cloudflare Pages (*.pages.dev). Users open the page, log in with Supabase, and use the app.
  • API → Cloudflare Worker (*.workers.dev). It checks the Supabase token and reads/writes D1.
  • Auth → Supabase. Login lives in the browser; the Worker only verifies the token.
  • Data → D1 (and any tables you created). Stored per user using the verified user id.
  • Payments (optional) → Stripe. The Worker uses your secret key to create checkout or portal links; the front end only redirects the user to Stripe.

To update the API: push to main → Worker redeploys. To update the front end: push to main → Pages redeploys from the public folder. One repo, full stack.
